# Tables

A table is a [model](models.md) of rows with typed cells, under a schema that is itself data. Everything it promises is built from [guards](transactions.md); nothing about a table is special to the layers beneath it.

## Rows

- A row is identified by a key its author chooses. Inserting requires the key to be vacant.
- Of two inserts to one key, the first in the [timeline](log.md) happens and the other is pruned.
- A change or delete targets the row its author read. A change written for a deleted row never applies to a later row under the same key.
- A row must therefore be read before it is changed or deleted. There is no blind overwrite of a row.

## Cells

- Each cell is written independently. Two transactions that change different columns of a row both happen.
- Of two that change the same column, the later in the timeline is what is read.
- Columns that must change together are guarded together; independence is the default, not a guarantee the author cannot refuse.
- A rule over one cell is checked by whoever writes it and whoever receives it.
- A rule over several cells or rows holds only as a [commit operation](commit-operations.md) or under a guard on each cell involved.

## Unique columns

- A value in a unique column is held by one row at a time. Of two rows that want it, the first in the timeline gets it.
- A row that loses a value loses its whole transaction.
- Holding a value is provisional until [committed](checkpoints.md). An application that tells a user a name is theirs waits for that.
- Identifiers that only need to be distinct are generated by their author and never contend.

## References

- A transaction may depend on a row existing, and is pruned if it does not.
- A referenced row cannot be deleted unconditionally: a delete and a reference written apart cannot both happen.
- Deleting a referenced row, with or without what refers to it, is a [commit operation](commit-operations.md).
- No peer can check alone that nothing anywhere refers to a row. That is why the delete waits for finality.
- Such a delete names the columns that hold references to the row. The rows found there at its place in the timeline are what refers to it.
- A reference placed after the delete is pruned with its transaction, since the row is gone.
- A row that would go with it, and is itself referenced, stops the delete.
- References are followed only within one [clock](groups.md).

## Rules

- A rule is a condition on the cells of a row that every row of a table meets.
- Putting a rule in force is a [commit operation](commit-operations.md). Lifting one is an ordinary [transaction](transactions.md).
- A transaction that would leave a row breaking a rule in force is pruned when it commits.
- A rule is judged against the row a transaction leaves, not the steps it took.
- A rule is not judged optimistically. What a row holds depends on the order of every write to it, which only a [checkpoint](checkpoints.md) fixes.
- An optimistic [read](reads.md) may therefore show a row that a rule will refuse.

## Indexes

- An index is derived state, kept locally by each peer that wants it; see [reads](reads.md).
- An index is never written by a transaction, so indexing a column does not change how its cells merge.
- Adding or dropping an index needs no agreement and no history.
- Rows and index entries are ordered, and a range of either is read directly.

## Numbers

- A quantity several devices spend from is split into allowances, one per contributor. Each spends its own without asking.
- A bound on the total holds because no allowance is overspent. Moving allowance between contributors is an ordinary transaction.
- An allowance is written only by its owner, so a spend within it is never pruned by what another device does.
- Allowance moved to a contributor is theirs once they accept it. Until then nobody spends it.
- A spend out of allowance that turns out never to have been given is pruned with it.
- A dense sequence, one with no gaps, is assigned only at commit.
- A row takes a number from a sequence once. A number is never given to a second row, even after the first is deleted.

## Schema

- Tables and columns are created, renamed, and dropped by operations in the timeline.
- A write depends on exactly the columns it names. Two devices that each add a column both succeed.
- A column's identity includes its type. Changing a type is adding a column.
- Changes that can invalidate concurrent work are covered in [migrations](migrations.md).
